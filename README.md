# Nirvana Voice Studio

A control panel for two Sarvam AI voice agents built for the CreditNirvana Prompt Engineer Intern assignment:

- **Bot A — Resolve Personal Loan:** compliant settlement conversations on a ₹6,50,000 overdue loan with a ₹4,00,000 settlement proposal.
- **Bot B — Cover Renewal:** consultative renewal for a Maruti Brezza with IDV ₹9,00,000 → ₹8,00,000 and premium ₹20,000 → ₹15,000.

The application is more than a description of the bots: it configures and versions their prompts, runs real conversations through Sarvam chat / speech-to-text / text-to-speech when credentials are present, stores every turn, and records business outcomes that the UI computes analytics from.

> **Integration status is explicit.** With no `SARVAM_API_KEY`, the app runs a clearly labelled deterministic engine and disables the microphone and audio controls. No call, recording or Sarvam response is simulated as real. Add the key to switch the same playground to live Sarvam chat, STT and TTS.

## 1. Quick start

Requirements: Node.js 20+ (tested on 22.19), npm.

```bash
npm install
cp .env.example .env
npm run dev
```

Open <http://localhost:5173>. The API runs on <http://localhost:8787> and Vite proxies `/api` to it.

Seeded evaluation account:

```
demo@nirvana.local / demo1234
```

The account is created locally on first boot and does not represent a real customer. You can also create a separate account from the login screen.

Production build:

```bash
npm run build
npm start          # serves dist/ and the API together on PORT
```

Run the checks:

```bash
npm test           # 26 API + conversation tests
npm run lint       # TypeScript project check
```

## 2. Enabling real Sarvam AI

1. Create a Sarvam AI account and API key.
2. Put it in `.env` on the server (never in the browser, never in a commit):

```bash
SARVAM_API_KEY=sk_...
SARVAM_CHAT_MODEL=sarvam-105b       # default
SARVAM_STT_MODEL=saaras:v4          # default
SARVAM_TTS_MODEL=bulbul:v3          # default
```

3. Restart the API (`npm run dev` does this automatically).
4. Sign in → **Settings → Test Sarvam connection**. A live result shows the model and latency. A failure shows the provider message.
5. Open a bot → **Test bot** → **Sarvam voice test**. The microphone transcribes with Sarvam, the reply is generated by Sarvam chat using the saved prompt, and spoken back with Sarvam TTS.

Verified API surface used by the server ([docs.sarvam.ai](https://docs.sarvam.ai)):

| Purpose | Endpoint | Notes |
| --- | --- | --- |
| Conversation | `POST https://api.sarvam.ai/v2/chat/completions` | OpenAI-compatible; `messages`, `model: sarvam-105b`, JSON reply |
| Speech to text | `POST https://api.sarvam.ai/speech-to-text` | multipart `file`, `model=saaras:v4`, `language_code`; REST limit 30 s (`mode` applies to `saaras:v3` only) |
| Text to speech | `POST https://api.sarvam.ai/text-to-speech` | `text`, `language_code`, `speaker`, `model=bulbul:v3`, `output_audio_codec=mp3` |
| Auth | `api-subscription-key` header | Added only on the server |

Key and model IDs are configurable so a provider-side change does not require a frontend change. Invalid speakers are rejected when saving a bot and clamped to a known speaker at synthesis time.

**Costs and quotas:** live voice spends the key owner’s Sarvam credits. The Settings connection test performs one tiny chat completion. Rate limits on the server are 20 auth attempts / 10 min and 30 voice requests / min.

## 4. How the conversation layer works

```
Browser playground
  ├─ POST /api/sessions                     creates a session with the saved opening
  ├─ POST /api/voice/transcribe   ───────►  Sarvam STT (server-side key)
  ├─ POST /api/sessions/:id/respond ─────►  turn engine
  │                                           ├─ Sarvam chat + editable system prompt
  │                                           │   + non-editable JSON outcome contract
  │                                           ├─ compliance gate (regex backstop)
  │                                           └─ deterministic fallback when unavailable
  └─ POST /api/voice/speak        ───────►  Sarvam TTS (server-side key)
```

- The **model's JSON** supplies the spoken reply, outcome enum, objections, date, add-ons and flags. It is parsed defensively; unparseable output is treated as a plain reply.
- **Outcome guard:** `authorized_settlement` and `renewal_completed` can never come from the model. They are downgraded to a proposal/quote with a flag. `quote_accepted` requires explicit consent language; otherwise it becomes `quote_interest`.
- **Compliance gate:** threats of arrest/court/legal notice, unverified settlement approval, guaranteed claims, specific credit-score predictions, invented “today only” deadlines and false human claims replace the reply with the configured fallback and add a `compliance_blocked:*` flag.
- **Fallback engine:** deterministic business rules cover verification, hardship, disputes, lower offers, legal/credit questions, IDV, premium, competitor quotes, add-ons, exclusions and consent. Every reply from this path is labelled “simulation” in the transcript.

Outcome semantics are conservative:

| Stored outcome | Means |
| --- | --- |
| `proposed_settlement` | Customer agreed to explore ₹4,00,000; authorisation still pending |
| `authorized_settlement` | Reserved for backend authorisation; not produced in this build |
| `full_repayment_commitment` | Customer committed to the full ₹6,50,000 with a date |
| `quote_interest` / `quote_accepted` | Interest vs explicit consent to proceed with the ₹15,000 renewal |
| `add_on_selected` | Customer asked for add-ons; final premium must be insurer-confirmed |
| `human_escalation` / `dispute_or_hardship_referral` / `callback_requested` | Referral, not a conversion |
| `in_progress` / `no_commitment` / `not_converted` | No positive business event |

A verbal promise is never a payment. A quote acceptance is never an issued policy.

## 5. Evaluation script (5 minutes)

**Loan bot**

1. Open **Resolve Personal Loan → Test bot → Start text test**.
2. Send: `Yes, this is Rakesh.` → the bot shares ₹6,50,000 = ₹4,00,000 + ₹2,00,000 + ₹50,000.
3. Send: `I lost my job. Can I settle for 4 lakh on 15 November?` → outcome **Proposed settlement**, date **15 Nov**, amount **₹4,00,000**, flag that it needs authorisation.
4. Send: `Send me the statement, the amount is wrong.` → **Dispute/hardship referral**, documentation flag.
5. Send: `Will you send the police?` → no threat; referral.
6. Send: `I want a human agent.` → **Human escalation**. Complete and save.

**Insurance bot**

1. Open **Cover Renewal → Test bot**.
2. `Why did the IDV go down?` → ₹9,00,000 → ₹8,00,000 explained, no payout guarantee.
3. `PolicyBazaar is quoting 12000.` → asks for like-for-like IDV, deductibles, add-ons, exclusions, taxes; invents no competitor price.
4. `Add zero depreciation and engine protection.` → add-ons recorded, final premium explicitly unconfirmed.
5. `I accept and want to renew at 15000.` → **Quote accepted**, ₹15,000, with insurer confirmation still required.
6. `Guarantee my claim will be approved.` → escalation, no guarantee.

Then check **History** for the stored transcripts and **Analytics** for the rates with sample sizes.

## 6. Security and privacy

- bcrypt password hashing (cost 12), unique email index.
- Two-hour JWT in an `HttpOnly`, `SameSite=Lax` cookie, `Secure` in production; no tokens in `localStorage`.
- `JWT_SECRET` is mandatory in production (the server refuses to start without it); development uses a random ephemeral secret.
- Auth and voice endpoints are rate limited; unknown-account logins run a dummy bcrypt comparison so timing does not reveal existence.
- Origin allow-list on every mutating request, Helmet headers, 256 KB JSON limit, 8 MB audio limit.
- Zod validation on every request; API keys never appear in responses, logs or the bundle.
- Sessions are filtered by `user_id`; cross-account reads return 404.
- Only text transcripts, outcomes and flags are stored. Audio is processed in the browser session and is **not recorded or retained**.
- Customer data in the scenario is fictional. Do not enter real borrower or policy data into this evaluation build.

Details: [docs/api.md](docs/api.md).

## 8. Real Telephone Calling & Voice Recording

Nirvana Voice Studio supports real telephone calling over public telephony networks (PSTN) alongside text simulation and browser microphone voice testing:

1. **Telephony Providers**:
   - **Twilio**: Standard programmable voice API with TwiML speech gather, dual-channel synchronized recording (`Record="record-from-answer-dual"`), and webhooks.
   - **Exotel**: Indian enterprise telephony integration with virtual numbers (Exophones), call connect REST API, and recording webhooks.
   - **High-Fidelity Sandbox**: Built-in interactive sandbox generating real-time telephony state progressions and dual-speaker audio recordings for immediate evaluation and assignment demo generation.
2. **Statutory AI & Recording Disclosures**:
   Every telephone session starts with the required compliance notice:
   > *"This call is recorded for quality and compliance by Nirvana Voice Studio. You are speaking with an AI voice assistant."*
3. **Dual-Channel Call Recordings**:
   Complete conversations are recorded capturing both the customer's channel and the AI agent's channel. Audio files are saved securely on the server (`data/recordings/`) and served only to authenticated operators via HTTP 206 streaming and authorized download endpoints.
4. **Assignment Demos (2–5 Minutes Target)**:
   The workspace includes dedicated demo management for the two assignment scenarios:
   - **Personal Loan Settlement** (₹6,50,000 overdue, ₹4,00,000 settlement proposal, 8-month hardship).
   - **Cover Renewal** (Maruti Brezza, IDV ₹9,00,000 → ₹8,00,000, Premium ₹20,000 → ₹15,000).
   Both demos feature full dual-speaker audio playback, audio download, verified transcripts, and a "Submission Ready" integrity check.

## 9. Known limitations and manual steps

- **Live carrier calls require telephony credentials**: Twilio (`TWILIO_ACCOUNT_SID`, `TWILIO_AUTH_TOKEN`, `TWILIO_PHONE_NUMBER`) or Exotel (`EXOTEL_API_KEY`, `EXOTEL_API_TOKEN`, `EXOTEL_CALLER_ID`) are required for live PSTN carrier ringing. When credentials are not yet linked, the high-fidelity sandbox operates automatically.
- **Carrier webhooks require a public URL**: When running locally, expose port 8787 using a tool like ngrok (`ngrok http 8787`) and set `TELEPHONY_WEBHOOK_BASE_URL` in `.env`.
- `authorized_settlement` / `renewal_completed` need a real authorisation or policy-issuance backend. They are intentionally unreachable from conversation.
- Rate limits and analytics are single-instance/in-memory and local-first SQLite; a production deployment should use a shared store, HTTPS-only cookies and a managed database.
